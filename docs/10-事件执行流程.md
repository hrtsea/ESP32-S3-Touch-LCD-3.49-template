# 10. 事件执行流程（运行时端到端）

> 本文档描述系统**运行时**的事件执行链路：从芯片启动、各任务编排，到数据流如何经事件总线贯通数据层与 UI 层，再到用户交互如何反向触发数据/配置变更。
>
> 事件总线**静态结构与接口**（事件 ID 清单、订阅 API、约束）见 [06-事件总线与数据流](./06-事件总线与数据流.md)。本文档聚焦"它实际怎么跑"。

---

## 10.1 任务编排总览

系统由若干 FreeRTOS 任务 + `esp_timer` 周期源组成，全部通过单一全局事件总线（`event_bus.c`）解耦通信：

| 角色 | 实体 | 节拍 / 触发 | 主要发布 | 主要订阅 |
|------|------|------------|---------|---------|
| 周期节拍源 | `nas_event_loop` 内部 `esp_timer`（原 `http_timer`, 2s） | 每 2s | `EVENT_TRIGGER_HTTP_FETCH` | — |
| 心跳源 | `event_bus` 内部 `esp_timer` | 1Hz / 10Hz | `EVENT_TICK_1HZ` / `EVENT_TICK_10HZ` | 任意 |
| 数据搬运 | `task_nas_data_loop`（`nas_event_loop.c`） | 被动消费队列 | `EVENT_NAS_DATA_UPDATE` | `TRIGGER_HTTP_FETCH` / `WIFI_CONNECTED/DISCONNECTED` / `HTTP_STOP` |
| 背景图抓取 | `bg_fetcher_task`（`bg_fetcher.c`） | 配置驱动 / `bg_refresh_s` 周期 | `EVENT_CLOCK_BG_CHANGED` | — |
| UI 消费 | `task_ui_event_loop`（`ui_events.c`） | 被动消费队列 | — | 8 类 UI 事件 |
| LVGL 渲染 | LVGL 内部 timer 任务 | 自身节拍 | — | — |
| WiFi 桥接 | `wifi_bridge` 回调 | WiFi 状态变化 | `EVENT_WIFI_*` | — |

> 关键事实：事件总线的两个路径——`event_bus_publish()` 仅入队（异步），`event_bus_publish_nas_data()` 先写 mutex 保护的 `s_nas_data_buffer` 再同步调 handler 并最终入队。UI 与数据层都各自跑独立任务，用 `event_bus_receive(portMAX_DELAY)` 阻塞等待，避免在发布者上下文操作硬件/UI。

## 10.2 启动序列（`app_main`）

`app_main()`（[main.cpp](./../main/main.cpp)）按以下顺序编排（与旧 `config/utils` 循环不同，这里**不使用** `cfg_start_event_loop`，改为逐个直接 start）：

```
app_main()
  ├─ nvs_flash_init()                       // 配置持久化后端
  ├─ app_cfg_init()                         // 载入 g_cfg（含 nas/smartctl/disk_config…）
  ├─ wifi_init()                            // 建立 WiFi，桥接 esp_wifi_config 事件 → EVENT_WIFI_*
  ├─ lvgl_init()                            // 显示屏 + LVGL 库初始化
  ├─ ui_init()                              // 构建 Boot 屏，注册 tileview/screen 手势事件
  ├─ bg_fetcher_ensure()                    // 若 bg_mode==2 则起 bg_fetcher_task
  ├─ nas_event_loop_start()                 // 起 task_nas_data_loop（任务栈 8192，见 nas_event_loop.c）
  ├─ nas_event_loop_timer_start()           // 2s 周期开始鸣放 EVENT_TRIGGER_HTTP_FETCH（原 http_timer）
  ├─ ui_events_start()                      // 起 task_ui_event_loop + 1Hz 时钟 timer
  └─ ui_Screen_Boot 显示（等待用户点按进入 Overview）
```

> 注意：`nas_event_loop` 任务虽已启动，但 `s_fetch_enabled` 初始为 `false`——真正允许抓数要等 `EVENT_WIFI_CONNECTED` 到达。因此在 WiFi 连上之前，`EVENT_TRIGGER_HTTP_FETCH` 会被丢弃（不发起 HTTP）。这是"无网不抓数"的节流点。栈大小调整（4096→8192）发生在 `nas_event_loop_start` 内的 `xTaskCreatePinnedToCoreWithCaps`，而非 `app_main`。

## 10.3 主干数据流：每 2 秒一次 NAS 刷新

这是系统最核心的执行链路（时序图与 [06 §6.5 事件发布时序（异步+同步）] 一致，此处展开调用栈与并发语义）：

```
[esp_timer 2s] fetch_timer_cb()   // nas_event_loop 内部定时器（原 http_timer_cb）
   └─ event_bus_publish(EVENT_TRIGGER_HTTP_FETCH)
        └─ xQueueSend(s_event_queue, &evt, 0)          // 非阻塞，队列满则丢
                     │
                     ▼  (唤醒)
[task_nas_data_loop] event_bus_receive(portMAX_DELAY)
   └─ xSemaphoreTake(s_fetch_mutex)
        ├─ 若 !s_fetch_enabled → 直接 return（WiFi 未连）
        └─ data_source_poll()                          // VTable → 当前 client（如 unraid_client 单次 GraphQL）
             ├─ http_client 轮询 ZettOS API
             ├─ 解析 JSON 填入 NasData（cpu/mem/disk/temp/net…）
             └─ 置 data->is_online
        ├─ 若 is_online:
        │    event_bus_publish_nas_data(data)           // 同步+异步双路径
        │       ├─ memcpy → s_nas_data_buffer (mutex 保护，补写 disk_slot_count)
        │       ├─ 同步调用 s_slots[EVENT_NAS_DATA_UPDATE] 的 handler
        │       │    （UI nas_data_sync_handler + rgb_nas_monitor；保证 UI 可靠收到数据）
        │       └─ xQueueSend(s_event_queue, &evt, 0)
        └─ xSemaphoreGive(s_fetch_mutex)
                     │
                     ▼  (唤醒)
[task_ui_event_loop] event_bus_receive(portMAX_DELAY)
   └─ case EVENT_NAS_DATA_UPDATE:
        UI_UPDATE(on_nas_data_update_evt(data))         // 宏内含 lvgl_lock(50)/lvgl_unlock()
           ├─ overview_screen_update_cpu(temp/mem/disk/hdd_led/hdd_name/network)
           └─ storage_screen_update_hdd_bar/temp/online
```

要点：
- **三层串行但跨任务**：timer → nas_loop → ui_loop，每层都在自己任务上下文，互不阻塞发布者（`publish_nas_data` 的同步 handler 段在 nas 任务上下文执行，经 `UI_UPDATE`/`lvgl_lock` 安全访问 LVGL）。
- **数据一致性**：UI 拿到的是 `s_nas_data_buffer` 的拷贝（同步路径已 memcpy），不会因 `s_fetch_mutex` 释放而产生悬空指针。
- **节流**：`s_fetch_enabled` 由 WiFi 事件翻转（见 10.4）。

## 10.4 网络状态驱动：抓取开关与 UI 联动

WiFi 状态变化是最典型的"一对多发"事件（`wifi_bridge` 把 `esp_wifi_config` 库事件桥接到事件总线）：

```
[esp_wifi_config 库]  CONNECTED / GOT_IP
   └─ wifi_bridge 回调 → event_bus_publish(EVENT_WIFI_CONNECTED)
                     │
                     ├─► [task_nas_data_loop]  s_fetch_enabled = true   // 打开抓取闸门
                     └─► [task_ui_event_loop]  UI_UPDATE(on_wifi_state_changed(true))
                                               → 刷新 IP 标签 + WiFi 图标颜色
```

- 断开时发 `EVENT_WIFI_DISCONNECTED`：nas_loop 置 `s_fetch_enabled=false`（停止抓数），UI 灰显图标。
- 旧有的 `WifiTab` / `WifiConfig` 走已废弃的 `event_bus_subscribe` 回调路径（见 [06 §6.4 模式 B]），仅用于设置页轻量刷新，建议迁移到队列模式。

## 10.5 配置变更：UI → 事件 → 多屏重建

用户在设置页改动配置（滑块/开关/保存）的闭环：

```
[UI 控件回调]  app_cfg_set_xxx(...)
   ├─ g_cfg.xxx = new
   ├─ cfg_publish(CFG_FIELD_XXX)
   │     └─ event_bus_publish(EVENT_CFG_CHANGED, &info, sizeof(info))
   ├─ event_bus_publish(EVENT_XXX_CHANGED, ...)   // 衍生事件（如 CLOCK_LAYOUT_CHANGED）
   └─ app_cfg_save()                               // 立即写 NVS
                     │
                     ▼
[task_ui_event_loop] 消费 EVENT_CFG_CHANGED / EVENT_*_CHANGED
   ├─ CFG_FIELD_BG_MODE/BG_URL 变化 → 若 bg_mode==2 调 bg_fetcher_ensure()
   ├─ EVENT_CLOCK_LAYOUT_CHANGED   → ui_clock 重建时钟显示
   ├─ EVENT_DISK_CONFIG_CHANGED    → destroy+init Overview/Storage 两屏（重建 HDD 控件数组）
   ├─ EVENT_SDCOPY_CONFIG_CHANGED  → destroy+init SDCopy 屏（重建 SD 拷贝控件）
   ├─ EVENT_FAN_CONFIG_CHANGED     → fan_control_apply_config(&app_cfg_get_fan())
   └─ EVENT_SHOW_FPS_CHANGED       → 显隐 FPS 标签
```

> 配置几乎都通过 `app_cfg` 模块统一发布（`cfg_publish`），UI 只在事件循环里被动消费，避免控件回调中直接重建 UI。

## 10.6 背景图抓取：`bg_mode==2` 的独立任务

背景图不占用主数据流，由独立低优先级任务完成（[bg_fetcher.c](./../main/utils/bg_fetcher.c)）：

```
[EVENT_CFG_CHANGED / 启动]  bg_fetcher_ensure()
   └─ 若 bg_mode==2 且有 bg_url：
        xTaskCreatePinnedToCoreWithCaps(bg_fetcher_task, 6KB, prio 4, Core 0)
                     │
                     ▼
[bg_fetcher_task]  等 WiFi(最多 12s) + sleep 2s
   loop:
     bg_fetch_once(g_cfg.bg_url)
       ├─ HTTP 流式下载到 /sdcard/clock_bg.bin.dl
       ├─ Magic 检测：仅接受 raw RGB565 面板字节序（PNG/JPEG 解码器已禁用，见文件头注释）
       ├─ rename 到 /sdcard/clock_bg.bin（先 unlink 旧文件）
       └─ event_bus_publish(EVENT_CLOCK_BG_CHANGED)
     sleep bg_refresh_s（可被 s_bg_fetcher_kick 提前唤醒；bg_refresh_s==0 则只抓一次）
                     │
                     ▼
[task_ui_event_loop]  case EVENT_CLOCK_BG_CHANGED → ui_clock 重新加载 canvas 背景
```

## 10.7 用户交互：手势与点击的闭环

UI 屏幕切换/详情跳转由 LVGL 事件回调直接完成（**不走事件总线**，属于进程内同步导航）：

```
[LVGL 输入] 手势/点击
   ├─ ui_events_register_tileview_events() → tileview_gesture_cb / tileview_commit_cb
   │     └─ 处理 tileview 边界回环（左/右滑切屏）
   ├─ ui_events_register_screen_events()   → activity_kick + scroll_stamp（记录交互时间戳）
   └─ 各屏 *_clicked / *_gesture 回调（如 ui_event_Screen_Overview_net_clicked）
         └─ ui_Screen_NetDetail_screen_init() + lv_scr_load_anim(...)   // 直接进入新屏
```

- 屏幕导航是**同步**的（直接 `lv_scr_load_anim`），因为回调本身就在 LVGL 任务上下文。
- 交互时间戳（`ui_helpers_notify_activity`）为未来的 `USER_ACTIVITY` / 息屏逻辑预留钩子（当前 `EVENT_USER_ACTIVITY` 消费者未接入）。

## 10.8 心跳与节能钩子

`event_bus` 内部两个 `esp_timer` 提供低成本节拍：

- `EVENT_TICK_1HZ`（1s）：时钟/日期刷新节拍来源。
- `EVENT_TICK_10HZ`（100ms）：高频轻量节拍（如动画、轮询状态）。

二者均入队，由消费方在各自任务内处理。UI 侧另起 `ui_events_start_time_timer()` 驱动时钟显示。

---

## 10.9 端到端时序小结

```
启动 → WiFi 连上(开闸) → [2s timer] → 抓数 → 同步写 buffer → 入队
     → UI 消费刷新 Overview/Storage
用户改配置 → 写 NVS + 发事件 → UI 重建对应屏
用户改 bg_mode=2 → 起 bg_fetcher → 抓图 → 发事件 → UI 换背景
用户滑屏/点击 → LVGL 直接切屏（不走总线）
```

## 10.10 调试要点

| 现象 | 排查方向 |
|------|---------|
| 屏不刷新 NAS 数据 | 确认 `s_fetch_enabled`（WiFi 已连？）；`EVENT_TRIGGER_HTTP_FETCH` 是否每 2s 发出 |
| 事件丢 | 单一 `s_event_queue`（容量 `EVENT_QUEUE_LEN=16`）混排所有事件，`xQueueSend(...,0)` 满则丢弃；`NasData` 走独立 `s_nas_data_buffer`（mutex 保护）不入队。消费慢会丢事件，查 `task_ui_event_loop` 是否被阻塞 |
| 改配置屏不更新 | 确认是否走了 `cfg_publish` 发布；`event_bus_subscribe` 已废弃（仅打 warn） |
| 背景图不换 | `bg_mode==2`？URL 非空？下载为 raw RGB565？`EVENT_CLOCK_BG_CHANGED` 是否发出 |
| 屏卡死 | `UI_UPDATE` 内 `lvgl_lock(50)` 超时 → 检查是否在其他任务直接调 LVGL |

> 事件名字符串用 `event_bus_name(id)` 打印，便于日志定位（见 [06 §6.2]）。
