# 13. 事件驱动分析：问题诊断与重构建议

> 本文档是对本项目事件驱动架构（基于 `main/utils/event_bus.c`）的**深度分析**，聚焦问题诊断与优化方向。
>
> 事件总线的**静态结构**与**接口**见 [06-事件总线与数据流](./06-事件总线与数据流.md)；**运行时端到端执行流程**见 [10-事件执行流程](./10-事件执行流程.md)。本文档补充二者未涉及的**缺陷分析**与**重构路线图**。
>
> 关联修复：本次分析源于"mock 数据源发布正常但 UI 不刷新"问题（详见下文 §3.1 与 §4.1）。

---

## 1. 架构现状速览

事件总线采用 **同步回调槽 + 异步队列** 双通道：

| 组件 | 位置 | 说明 |
|------|------|------|
| `s_event_queue` | `event_bus.c:29` | FreeRTOS Queue，长度 `EVENT_QUEUE_LEN=16`，元素 `event_t`，**非阻塞投递** |
| `s_slots[]` | `event_bus.c:26` | 同步回调槽位，每事件 `MAX_HANDLERS_PER_EVENT=8` 个 handler |
| `s_mux` | `event_bus.c:27` | 保护 `s_slots` 的互斥锁 |
| `s_nas_data_buffer` | `event_bus.c:30` | 静态全局 `NasData` 缓冲（NAS 数据指针的稳定宿主） |
| `s_nas_data_mux` | `event_bus.c:31` | 保护 NAS 缓冲的互斥锁 |
| tick 定时器 | `event_bus.c:32-33` | 1Hz / 10Hz 周期源（`ESP_TIMER_ISR` dispatch） |

**两条传播通道：**

1. **异步队列**：`event_bus_publish(id, data, len)` → `xQueueSend(..., 0)` 非阻塞入队 → 消费者任务 `event_bus_receive()` 出队。
2. **同步回调**：仅 `event_bus_publish_nas_data()` 在入队前，额外遍历 `s_slots[EVENT_NAS_DATA_UPDATE]` 同步调用 handler。

> **关键结论**：
> - `event_bus_publish()` **只入队，不走同步回调**（`event_bus.c:141-157`）。
> - `event_bus_publish_nas_data()` **同时走同步 handler + 入队**（`event_bus.c:159-190`）。
> - `xQueueSend(..., 0)` 是**非阻塞**投递，队列满时直接丢弃（返回值被忽略）。

## 3. 问题清单（按严重程度）

### 🔴 P0-1：共享队列多消费者竞争 → 事件丢失（已修复，根因仍在）

- **现象**：mock 数据源每 2 秒发布 `NasData`（日志正常打印 `publishing NasData`），但 UI 界面数值不刷新。
- **根因**：`EVENT_NAS_DATA_UPDATE` 入队到共享队列后，出队时 FreeRTOS 可能唤醒 `task_nas_data_loop`（同优先级 1）。nas 任务只处理 `TRIGGER_HTTP_FETCH` / `WIFI_*` / `HTTP_STOP`，`EVENT_NAS_DATA_UPDATE` 落入其 `switch` 的 `default:` 分支被**直接丢弃**，UI 任务永远拿不到。
- **修复**（本次已完成）：恢复 `event_bus_subscribe` 真实实现，并让 UI 通过 `event_bus_subscribe(EVENT_NAS_DATA_UPDATE, nas_data_sync_handler, NULL)` 走**同步回调**，绕开队列竞争。已验证每次发布都直达 UI。
- **遗留**：**根本缺陷仍在**——任何"队列消费方 A 不关心的事件"都可能被 A 抢走丢弃，而消费方 B 永远收不到。当前仅 `NAS_DATA_UPDATE` 有同步兜底。

### 🔴 P0-2：事件语义不清——"数据"与"信号"混用同一队列

- `EVENT_NAS_DATA_UPDATE`（带指针的**数据事件**）与 `EVENT_TICK_1HZ` / `USER_ACTIVITY`（无载荷的**轻量信号**）混在一个 16 长度队列。
- 高频信号（1Hz + 10Hz + 触摸）会**挤压**低频数据事件。
- 队列满时 `xQueueSend(..., 0)` 直接丢弃，无背压、无统计。

### 🟠 P1-1：`TICK_*` 事件入队但无消费者

- `EVENT_TICK_1HZ` / `EVENT_TICK_10HZ` 由 ISR 周期入队，但搜索 `case EVENT_TICK_` **无任何消费者处理**。
- UI 时钟刷新用的是独立 `lv_timer_create`（`ui_events.c` `time_update_timer_cb`），不依赖 TICK 事件。
- 结论：TICK 事件是**无效负载**，纯粹占用队列，加剧队列满风险。

### 🟠 P1-2：ISR 上下文调用 `xQueueSend`

- tick 定时器使用默认 `ESP_TIMER_ISR` dispatch，回调在 **ISR 上下文**调 `event_bus_publish` → `xQueueSend(..., 0)`。
- 虽然非阻塞 + 返回值被忽略目前不致命，但若将来改为阻塞等待、加日志或同步调用，会违反 FreeRTOS "ISR 中应使用 `xQueueSendFromISR`" 的规则。

### 🟠 P1-3：事件数据指针生命周期隐患

- `event_t.data` 是**原始指针**。部分发布者传**栈/局部变量地址**（如 `app_cfg.c` 的 `EVENT_TILE_CHANGED` 传 `&idx` 局部变量）。
- 入队后，消费方异步读取时发布者的栈可能已失效 → **未定义行为**（use-after-stack）。
- `EVENT_NAS_DATA_UPDATE` 因指向静态全局 `s_nas_data_buffer` 是安全的，但其他带数据事件存在此风险。

### 🟡 P2-1：`event_bus_subscribe` 曾是被废弃的空壳

- 同步回调通道（`s_slots`）设计存在，但 `subscribe` 被误实现为只打警告日志的空壳（`event_bus.c:106-112`）。
- 导致 `rgb_nas_monitor`、`WifiConfig`、`WifiTab` 的同步订阅**此前全部静默失效**。
- **连带影响（本次已恢复）**：恢复后这些订阅被激活，需验证行为是否符合预期（例如 RGB LED 现在会响应 NAS 数据更新）。

### 🟡 P2-2：`event_bus_publish` 隐式初始化副作用

- `event_bus_publish` 内 `if (!s_inited) event_bus_init()`，任何早期发布都会隐式启动 tick 定时器，副作用隐蔽。

### 🟢 P3-1：存在被发布但无消费者的事件

- `EVENT_FAN_STATUS_UPDATE`（`fan_control.c:236` 发布）无 `case EVENT_FAN_STATUS_UPDATE` 消费者。
- `EVENT_USER_ACTIVITY` 发布者多，但消费逻辑依赖其他机制（dim_timer 独立计时）。

## 4. 已实施的修复

### 4.1 NAS 数据事件改走同步回调（P0-1）

- `main/utils/event_bus.c`：恢复 `event_bus_subscribe` / `event_bus_unsubscribe` 的真实实现（注册到 `s_slots` 槽位，受 `s_mux` 保护）。
- `main/ui/ui_events.c`：
  - 新增 `nas_data_sync_handler(const event_t*, void*)`，内部 `UI_UPDATE(on_nas_data_update_evt(data))`。
  - `ui_events_start()` 中 `event_bus_subscribe(EVENT_NAS_DATA_UPDATE, nas_data_sync_handler, NULL)`。
  - 移除 `task_ui_event_loop` 里对 `EVENT_NAS_DATA_UPDATE` 的队列消费 case，避免与同步回调重复处理。

> 验证：日志中 `publishing NasData` 后紧跟 `ui_events: [ui disk] ...`，证明同步回调每次都被执行。

### 4.2 已知边界

- 同步回调在**发布者线程**（nas 任务）上下文执行，`UI_UPDATE` 用 `lvgl_lock(50)`。若 LVGL 主循环持有锁超过 50ms，本次更新会被跳过（下个周期补上）。mock 场景影响极小，但真实 NAS + 复杂渲染场景需评估。

## 5. 重构建议（按优先级）

### 建议 1（推荐，根治 P0-1）：为队列消费者提供事件过滤，消除竞争

- 扩展 `event_bus_receive` 或新增 `event_bus_receive_filtered(event_t*, uint32_t mask, TickType_t)`。
- `task_nas_data_loop` 只取自己关心的事件（`TRIGGER_HTTP_FETCH`/`WIFI_*`），其余事件**留在队列**给 UI 任务，从根上杜绝"抢走他人事件并丢弃"。

### 建议 2（推荐，解决 P0-2）：按语义拆分通道

- 区分"数据事件"（可靠送达，走同步回调）与"信号事件"（可丢弃，走队列）。
- 提供两个发布 API：`event_bus_publish_data()`（同步 + 可选队列冗余）与 `event_bus_publish_signal()`（仅入队）。
- `EVENT_NAS_DATA_UPDATE` 归为数据事件，`TICK_*` / `USER_ACTIVITY` 归为信号事件。

### 建议 3（重要，解决 P1-1）：消除 TICK 无效入队

- 确认 `TICK_1HZ` / `TICK_10HZ` 确无消费者后，将其从队列发布中移除，或改为直接回调，避免每 100ms 无效占用队列。

### 建议 4（重要，解决 P1-2）：ISR 安全

- 将 tick 定时器改为 `ESP_TIMER_TASK` dispatch（与 `nas_event_loop` 拉取定时器一致），或在发布前用 `xPortInISRContext()` 判断、ISR 内改用 `xQueueSendFromISR`。

### 建议 5（重要，解决 P1-3）：修复事件数据指针生命周期

- 数据事件统一用静态/堆缓冲（同 `s_nas_data_buffer` 模式）。
- 或让 `event_t` 内嵌小数据缓冲（传值拷贝），规定发布者不得传栈地址。

### 建议 6（适度）：队列背压与监控

- 队列满时记录统计/告警日志，而非静默丢弃；暴露 `event_bus_get_queue_fill()` 便于调试。

### 建议 7（低）：清理

- 验证 `rgb_nas_monitor` 与 `WifiConfig`/`WifiTab` 的同步订阅恢复后行为是否符合预期。
- 补全 `EVENT_FAN_STATUS_UPDATE` 的消费者或移除发布。
- 消除 `event_bus_publish` 内隐式 `event_bus_init` 的副作用（改为显式初始化）。

## 6. 建议优先级总表

| 优先级 | 动作 | 影响 | 建议对应项 |
|--------|------|------|-----------|
| 立即 | 保留已完成的 NAS_DATA_UPDATE 同步回调修复 | 已解决 UI 不刷新 | §4.1 |
| 高 | 队列消费者事件过滤 | 根治竞争，避免未来事件丢失 | 建议 1 |
| 高 | 移除 / 处理 TICK 无效入队 | 降低队列压力 | 建议 3 |
| 高 | 事件指针生命周期 | 消除未定义行为 | 建议 5 |
| 中 | ISR 安全、事件语义拆分 | 健壮性 / 可维护性 | 建议 4 / 2 |
| 低 | 背压监控、清理死订阅 | 可维护性 | 建议 6 / 7 |
